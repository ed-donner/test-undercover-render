# Code standards

## General

1. Keep it simple, do not overcomplicate.
2. Comments only when necessary.
3. Be concise: a short README and no emojis.
4. IMPORTANT: avoid overly defensive code. Handle exceptions only when necessary.
5. Use uv: ALWAYS `uv run`, NEVER `python3`.
6. TypeScript: strict mode, never `any`.

## Structure

7. One way to do each thing. The agent reaches the backend only through `agent/api.py`, and the improver only through `agent/improver_api.py`, both on the one client in `agent/connection.py`, the one place with the backend's address. The claim agent's tools and its payment take one route, chosen by `agent/tool_route.py` when a run's claim agents are built, and the Copilot's context layer tools the same route, chosen as a turn is built: `agent/gateway.py`, the AgentCore Gateway's MCP tools signed with SigV4, when `UNDERCOVER_GATEWAY_URL` is set, or else `agent/direct.py`, straight to the app through `agent/api.py` and to the context layer over MCP. Each route is one module, both are what `agent/routes.py` says a route is, and MCP tools are called only through `agent/mcp_tools.py`. `UNDERCOVER_GATEWAY_URL`, the Gateway's `___` and `bedrock-agentcore` are written in `gateway.py` alone, `UNDERCOVER_CONTEXT` and the context layer's address on the laptop in `direct.py` alone, and the targets' names in `routes.py` alone. The agent reaches its memory of each customer only through `agent/memory.py`, the one place with `UNDERCOVER_MEMORY_ID` and the memory's namespaces, and the Copilot its memory of each handler only through `agent/copilot/memory.py`, the one place with `UNDERCOVER_COPILOT_MEMORY_ID` and the handlers' namespaces, both on the AgentCore store in `agent/agentcore_memory.py`. The Copilot reaches the backend only through `agent/copilot/app_api.py`, one function per operation, each sending the handler's sign-in with `connection.call_as` and never the agent's key. Everything else the agent sends the backend, its bookkeeping included, goes through `agent/api.py` with the key. The dashboard reaches the backend only through `dashboard/src/api.ts`, on `dashboard/src/connection.ts`, the one place that sends a request and reads its answer or refusal, which nothing else uses, and Supabase Auth only through `dashboard/src/auth.ts`. Each API module has one function per backend operation, named after it. The agent reaches AgentCore Identity only through `agent/identity.py`, the one place with `AGENTCORE_CREDENTIAL_` and `requires_api_key`. The backend reaches the agent only through `backend/agent_service.py` and the Copilot only through `backend/copilot_service.py`, one function per operation, each sending one payload on one of two routes chosen per call: the AgentCore app's `/invocations` on the laptop, at `UNDERCOVER_AGENT` with the key or at `UNDERCOVER_COPILOT` with none, or its runtime through boto3's `invoke_agent_runtime` when `UNDERCOVER_AGENT_RUNTIME` or `UNDERCOVER_COPILOT_RUNTIME` names one; each service's settings are written in its module alone, and `/invocations` and the `bedrock-agentcore` client in `backend/runtime_calls.py`, which both use, alone. Committing what the app did for some work, asking for it to be taken and undoing it when it wasn't is `backend/asking.py`'s. What the app knows of the agent's work, such as how long it may go quiet, is `backend/agent_work.py`'s, and what it keeps of the Copilot's conversations `backend/conversations.py`'s. The backend reaches the judge only through `backend/judge.py`. The base URL and each path are written once, there, and no other module builds a URL or sends a request.
8. Each module has one job, and its name says what it is. A module uses another through what that module is for, and never borrows its helpers. A helper two modules need goes in a module of its own. No circular imports. Tests follow the same rule: shared test helpers live in their own module, never in another test file.
9. Write a literal once. A URL, a path, a status or a message used in more than one place is named once, in the module that owns it.
10. Use the framework's own way before writing your own: FastAPI dependencies and models, `BedrockAgentCoreApp`'s entrypoint, async tasks and `/ping` for the agent's operations, a Pydantic discriminated union for their payloads, LangGraph's `interrupt()`, `Command(resume=...)` and `get_state().interrupts` for a handler's answer, LangChain's `context_schema` with `ToolRuntime` for what a tool needs to know, LangGraph's `StateGraph`, `ToolNode`, conditional edges, `RetryPolicy` and checkpointer for the claim agent and the Copilot, LangGraph's `Send`, `max_concurrency` and `RetryPolicy` for the dispatcher, LangChain's `create_agent` with `HumanInTheLoopMiddleware`, `ModelCallLimitMiddleware` and middleware hooks for the improver, a LangGraph store passed at compile for the memory, tool artifacts for the steps a tool records, `MultiServerMCPClient` for MCP tools, FastMCP for the context layer's server, SQLAlchemy Core for the database, with a conditional update that checks its row count for a move only one caller may make, React hooks and shared components. Check the documentation for the installed version.
11. A function does one job. Split one that mixes levels of detail, such as setting up a run, driving the agent and recording the result.
12. When you extend code, bring it up to these standards first. Never copy a pattern they rule out.

## The agent

13. The agent's parts are kept apart. `connection.py`, `api.py` and `improver_api.py` are the backend's API, with the app's words for its records in `app_terms.py` and how a model is told a refusal in `refusals.py`, which use nothing else in the agent, and `routes.py`, `gateway.py`, `direct.py` and `mcp_tools.py` are the claim agent's two routes to its tools and its payment, which use nothing else in the agent but `direct.py`'s use of `api.py`. `memory.py` is the claim agent's memory of each customer, which uses nothing else in the agent but `agentcore_memory.py`, and the claim graph reads it as its LangGraph store. `tools.py` holds the claim agent's tools, with the context layer's seven lookups from `context_tools.py`, which both agents have, and the context and state the tools read, and the tools reach the app only through the claim agent's route, filling in the claim, its policy and its customer from the context rather than taking them from the model. `harness.py` builds and runs the claim agent, on the route `tool_route.py` chooses and the checkpoints `checkpoints.py` keeps, and the claim graph's nodes do what middleware would. `dispatcher.py` works a dispatch or an evaluation with no model, and reaches the claim agent only through the harness's one function, `work_in_run`. `improver.py` is the improver, with its tools, its middleware and the context they read; it never imports the harness, the dispatcher or the routes, and works a round's evaluations through a function the entry point hands it. `entrypoint.py` is the agent's AgentCore app: it gets ready on its first request, checks the key off Runtime, reads each operation's payload, and hands the work to `work.py` on a thread of its own, registered as an async task, with the plumbing both AgentCore apps share in `agentcore_app.py`. `work.py` works a run through the dispatcher, a round through the improver and a resume through the harness, each telling the app every minute while it goes on, and the app why it stopped when it fails. `identity.py` fetches the agent's credentials from AgentCore Identity on Runtime, `heartbeat.py` tells the app every minute that a piece of work is still going, and `handler_answer.py` reads a handler's answer to a held approval from the claim and gives the model a note sent back; each uses nothing else in the agent. Rules about claims and payments are enforced by the backend and the Gateway's Policy, whatever the agent does.
14. Instructions give an agent its goal, what it has to work from and what done looks like. They don't script its steps: it plans those itself. Anything that must always happen, or happen in a fixed order, is done by the code.

## The Copilot

15. The Copilot is a part of its own, in `agent/copilot/`, with the same rules as the claim agent. Of the rest of the agent it uses only `connection.py`, through `app_api.py`, its API on the app and the only one of its modules that uses it, and the shared modules, `checkpoints.py`, `tool_route.py`, `context_tools.py`, `agentcore_memory.py`, `agentcore_app.py` and `identity.py`, with `app_terms.py`, the app's words for its records that both agents read, `refusals.py`, `routes.py`, `openrouter.py`, `json_text.py` and `console.py`; nothing in the claim agent imports it. `tools.py` holds its tools and the context they read: the handler's sign-in, the handler as the app gave them, the conversation, the turn and the route, which reach the graph and the tools in LangGraph's context and are never saved. `cards.py` records each step as a card with the app. `graph.py` is its hand-written LangGraph graph: the model, a `ToolNode`, the sign-off checked in code, paused with `interrupt()` in a node of its own and signed off or canceled in code. `turns.py` works a turn and an answer to a confirmation and tells the app how each ended. `waiting.py`, `needs_a_handler.py` and `criteria.py` wait for the agent's work, work out what needs a handler and check the success criteria, all in code. `memory.py` is its memory of each handler. `entrypoint.py` is its AgentCore app: it gets ready on its first request, checks the handler's sign-in and the turn with the app before it answers, keeps one turn at a time for each conversation in its process, and hands the turn to `turns.py` on a thread of its own, registered as an async task. It asks for no key, since everything it does carries the handler's sign-in. Rules about claims and payments are enforced by the backend, whatever the Copilot does.
16. What must always happen is code: the check of the sign-in, the memory's lookup and save, the check before a sign-off's pause, the pause itself, the answer after a Cancel, the waits, and the whole answer on the success criteria. The Copilot's instructions give it its goal, who it works for, what it can see and do, the success criteria and how to answer.
17. The sidebar is the dashboard's part of the Copilot: `components/Copilot.tsx` and its parts, with the conversation's shape and how it's read in `conversation.ts`, and what the sidebar shows and remembers in `copilot.ts`. It reads and sends through `api.ts`, with `useLoad` and `useAction`, like every page, and shows only what the app's records say: a sign-off shows as paid only from the turn's own card for it, done.
