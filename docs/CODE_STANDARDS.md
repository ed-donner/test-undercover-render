# Code standards

## General

1. Keep it simple, do not overcomplicate.
2. Comments only when necessary.
3. Be concise: a short README and no emojis.
4. IMPORTANT: avoid overly defensive code. Handle exceptions only when necessary.
5. Use uv: ALWAYS `uv run`, NEVER `python3`.
6. TypeScript: strict mode, never `any`.

## Structure

7. One way to do each thing. The agent reaches the backend only through `agent/api.py`, and the improver only through `agent/improver_api.py`, both on the one client in `agent/connection.py`, the one place with the backend's address. The claim agent's tools and its payment take one route, chosen when a run's claim agents are built: `agent/gateway.py`, the AgentCore Gateway's MCP tools signed with SigV4, when `UNDERCOVER_GATEWAY_URL` is set, or else `agent/direct.py`, straight to the app through `agent/api.py` and to the context layer over MCP. Each route is one module, both are what `agent/routes.py` says a route is, and MCP tools are called only through `agent/mcp_tools.py`. `UNDERCOVER_GATEWAY_URL`, the Gateway's `___` and `bedrock-agentcore` are written in `gateway.py` alone, `UNDERCOVER_CONTEXT` and the context layer's address on the laptop in `direct.py` alone, and the targets' names in `routes.py` alone. The agent reaches its memory of each customer only through `agent/memory.py`, the one place with `UNDERCOVER_MEMORY_ID` and the memory's namespaces. Everything else the agent sends the backend, its bookkeeping included, goes through `agent/api.py` with the key. The dashboard reaches the backend only through `dashboard/src/api.ts`, and Supabase Auth only through `dashboard/src/auth.ts`. Each API module has one function per backend operation, named after it. The agent reaches AgentCore Identity only through `agent/identity.py`, the one place with `AGENTCORE_CREDENTIAL_` and `requires_api_key`. The backend reaches the agent only through `backend/agent_service.py`, one function per operation, each sending one payload on one of two routes chosen per call: its AgentCore app's `/invocations` at `UNDERCOVER_AGENT` on the laptop, with the key, or its runtime through boto3's `invoke_agent_runtime` when `UNDERCOVER_AGENT_RUNTIME` names one; those settings, `/invocations` and the `bedrock-agentcore` client are written there alone. What the app knows of the agent's work, such as how long it may go quiet, is `backend/agent_work.py`'s. The backend reaches the judge only through `backend/judge.py`. The base URL and each path are written once, there, and no other module builds a URL or sends a request.
8. Each module has one job, and its name says what it is. A module uses another through what that module is for, and never borrows its helpers. A helper two modules need goes in a module of its own. No circular imports. Tests follow the same rule: shared test helpers live in their own module, never in another test file.
9. Write a literal once. A URL, a path, a status or a message used in more than one place is named once, in the module that owns it.
10. Use the framework's own way before writing your own: FastAPI dependencies and models, `BedrockAgentCoreApp`'s entrypoint, async tasks and `/ping` for the agent's operations, a Pydantic discriminated union for their payloads, LangGraph's `interrupt()`, `Command(resume=...)` and `get_state().interrupts` for a handler's answer, LangChain's `context_schema` with `ToolRuntime` for what a tool needs to know, LangGraph's `StateGraph`, `ToolNode`, conditional edges, `RetryPolicy` and checkpointer for the claim agent, LangGraph's `Send`, `max_concurrency` and `RetryPolicy` for the dispatcher, LangChain's `create_agent` with `HumanInTheLoopMiddleware`, `ModelCallLimitMiddleware` and middleware hooks for the improver, a LangGraph store passed at compile for the memory, tool artifacts for the steps a tool records, `MultiServerMCPClient` for MCP tools, FastMCP for the context layer's server, SQLAlchemy Core for the database, with a conditional update that checks its row count for a move only one caller may make, React hooks and shared components. Check the documentation for the installed version.
11. A function does one job. Split one that mixes levels of detail, such as setting up a run, driving the agent and recording the result.
12. When you extend code, bring it up to these standards first. Never copy a pattern they rule out.

## The agent

13. The agent's parts are kept apart. `connection.py`, `api.py` and `improver_api.py` are the backend's API, and `routes.py`, `gateway.py`, `direct.py` and `mcp_tools.py` are the claim agent's two routes to its tools and its payment, which use nothing else in the agent but `direct.py`'s use of `api.py`. `memory.py` is the claim agent's memory of each customer, which uses nothing else in the agent, and the claim graph reads it as its LangGraph store. `tools.py` holds every tool of the claim agent and the context and state the tools read, and the tools reach the app only through the claim agent's route, filling in the claim, its policy and its customer from the context rather than taking them from the model. `harness.py` builds and runs the claim agent, chooses its route, and the claim graph's nodes do what middleware would. `dispatcher.py` works a dispatch or an evaluation with no model, and reaches the claim agent only through the harness's one function, `work_in_run`. `improver.py` is the improver, with its tools, its middleware and the context they read; it never imports the harness, the dispatcher or the routes, and works a round's evaluations through a function the entry point hands it. `entrypoint.py` is the agent's AgentCore app: it gets ready on its first request, checks the key off Runtime, reads each operation's payload, and hands the work to `work.py` on a thread of its own, registered as an async task. `work.py` works a run through the dispatcher, a round through the improver and a resume through the harness, each telling the app every minute while it goes on, and the app why it stopped when it fails. `identity.py` fetches the agent's credentials from AgentCore Identity on Runtime, `heartbeat.py` tells the app every minute that a piece of work is still going, and `handler_answer.py` reads a handler's answer to a held approval from the claim and gives the model a note sent back; each uses nothing else in the agent. Rules about claims and payments are enforced by the backend and the Gateway's Policy, whatever the agent does.
14. Instructions give an agent its goal, what it has to work from and what done looks like. They don't script its steps: it plans those itself. Anything that must always happen, or happen in a fixed order, is done by the code.
