# Status

The claims pilot in `docs/PLAN.md`, the harness in `docs/PLAN_HARNESS.md` and durable state in `docs/PLAN_DURABLE.md` are built: all six phases of each are done. The swarm and the scoreboard in `docs/PLAN_SWARM.md` are built too: all six phases are done. The improver and sign-in in `docs/PLAN_IMPROVE.md` are built: all seven phases are done: handlers sign in, the claim agent's configuration is kept in versions, the platform's settings are on a Settings page, a judge grades each evaluated claim's explanation, and a senior handler runs rounds of the improver on the Improvement page, approving or rejecting each change and recipe it proposes. A dispatcher with no model works the queue with up to 25 claim agents at once, on GPT-6 Luna by default, recording the cost and time of every claim, and a Scoreboard scores evaluations on copies of the labeled claims. The security changes in `docs/PLAN_SECURE.md` are built: all five phases are done: the agent's side identifies itself to the backend with an API key, a second model checks each claim for instructions hidden in it before the claim agent's model sees it, the backend serves the claim agent's own API document for the Gateway, a handler's sign-off pays a held payout, and the backend and the dashboard are ready for AWS Lambda. The context layer, memory and the Gateway in `docs/PLAN_CONTEXT.md` are built: all six phases are done. The claim agent works from three sources of data: the context layer in `context/`, an MCP server of its own with seven read-only lookups over data governance's files, each answer naming its files and their sources; its memory of each customer in AgentCore Memory, when `UNDERCOVER_MEMORY_ID` is set and outside evaluations; and the app's records. Its tools and its payment go through the AgentCore Gateway when `UNDERCOVER_GATEWAY_URL` is set, signed with the AWS CLI's credentials, or straight to the app and the context layer otherwise, taking no ids from the model, and a payment the Gateway refuses waits for a handler's sign-off. Seeding loads the plans and the two documents from `context/`, and the app no longer serves the documents. Every decision record meets claims manual section 14, with its calculation, who or what made it, when, and the manual's version. The claim page shows every lookup and where it came from, every memory search and save, every refusal, a Context used panel and the whole decision record.

Sending claims back and the agent on AgentCore Runtime, in `docs/PLAN_RUNTIME.md`, is built: all four phases are done, and its live checks pass. An approval held for sign-off pauses the claim graph with LangGraph's `interrupt()`. A senior handler signs it off, which pays it and asks the agent to resume the claim, ending the agent's work on it, or sends it back with a note, which the agent reads as a senior handler's review before it decides again. The agent is an AgentCore app, `agent/entrypoint.py`, which `npm run dev` serves on port 8080 and `runtime/main.py` runs on AgentCore Runtime, and the app reaches it at `/invocations` with the agent's key, or through `invoke_agent_runtime` when `UNDERCOVER_AGENT_RUNTIME` names its runtime. The app, not the agent, keeps one dispatch, evaluation or working round going at a time: it creates the runs and the rounds and records the reviews, then asks the agent to work them by id, and the agent tells it every minute that it's still working.

The Copilot in `docs/PLAN_COPILOT.md` is built: all six phases are done, and its live checks pass but one. Explaining why a held payout needs a handler, it drew on the claim, the agent's steps, the policy and the settings but never read the context layer itself, though its instructions set it that goal (see the known gaps and the last live run). The app keeps the Copilot's conversations, their turns and each turn's cards, and passes a handler's sign-in on to the Copilot with each message and each answer to a confirmation, on the laptop or on AgentCore Runtime in the conversation's session. The Copilot, `agent/copilot/`, is a hand-written LangGraph graph that works a turn as the handler who asked: it looks things up in the app and the context layer, starts dispatches and evaluations, sends held decisions back, and pauses a sign-off for the handler's confirmation, each step a card in the app. It waits for the work it starts in code, says what needs a handler, answers whether we meet the success criteria with a table written in code, and remembers each handler. It is an AgentCore app of its own, `agent/copilot/entrypoint.py`, which `npm run dev` serves on 127.0.0.1:8081 and `runtime/copilot.py` runs on AgentCore Runtime as the platform team's second runtime, `copilot`. Every signed-in page has the Copilot in a sidebar on the right. `docs/CODE_STANDARDS.md`, `docs/TECH_STACK.md` and `docs/PROCESS.md` describe the Copilot and the parts the two agents share.

## Running it

- After pulling the security changes, reseed with `npm run seed`: a claim signed off but not yet paid under the old flow can't be paid any more.
- `.env` needs `UNDERCOVER_API_KEY`, the agent's API key, a random value of at least 32 characters such as one from `secrets.token_urlsafe(32)`; the agent doesn't get ready without it.
- After pulling the context layer, reseed with `npm run seed`: the documents table has a version, and the decisions and steps have new columns.
- After pulling the send back and the agent on Runtime, reseed with `npm run seed`: claims, runs and rounds have new columns, and there are `sent_back_decisions` and `locks` tables.
- After pulling the Copilot, reseed with `npm run seed`: there are `conversations`, `copilot_turns` and `copilot_steps` tables.
- `npm run dev` starts the backend on port 8000, the agent's AgentCore app on port 8080 (stop Lab 1's `agentcore dev` first, which uses the same port), the Copilot's AgentCore app on 127.0.0.1:8081, the context layer on port 8006 (`uv run -m context`, at http://127.0.0.1:8006/mcp) and the dashboard on http://localhost:5173. It passes `.env` to the backend, the agent and the Copilot, so it needs a `.env`. With `DATABASE_URL` there the backend uses Supabase; the agent and `uv run -m agent` always need it, since they save the claim graph's progress there. `uv run --env-file .env --isolated --only-group runtime python -m runtime.main` serves the agent the way AgentCore Runtime starts it, on the same port.
- `npm run seed` rebuilds the database `npm run dev` uses from `data/`, with the plans and the two documents from `context/`, putting every claim back in the queue and emptying the dispatches and evaluations. The queue's 26 claims include the security team's CLM-1901 from `data/security/`, whose handler's decision is never seeded. It also stores the held-out claims and the handlers' decisions on both labeled sets from `data/evals/`, which nothing else reads. It drops the old `todos` table first when it's there. `uv run -m backend.seed` alone never reads `.env` and rebuilds the SQLite file `undercover.db`, as the end-to-end tests do. The backend only seeds a database with no tables, so reseed after pulling a change to the tables.
- If you're on a free model, set `MODEL_NAME` in `.env` before `npm run seed`: seeding chooses version 1 of the claim agent and the models allowed from it.
- Every page needs a signed-in handler. Sign in on `/sign-in` with a handler's email from `data/handlers.json` and the password set for them in Supabase Auth (`HANDLER_PASSWORD` in `.env`). There's no sign-up. Dana Whitfield is the only handler who can sign off payouts over the limit.
- `npm run build` builds the dashboard into `dashboard/dist`, with the Supabase address and publishable key from `.env`. When the folder exists, the backend serves it at `/` beside the API, so `uv run --env-file .env -m uvicorn backend.main:app` alone serves the whole app at http://127.0.0.1:8000; `npm run dev` is unchanged. `docs/TECH_STACK.md` describes the deployment.
- On the queue page, choose the claim agents at once, from 1 to 25, and press Start a dispatch. The app creates the dispatch and asks the agent to work it, and the agent works every claim in progress, waiting or sent back with up to N claim agents at once. Only one dispatch, evaluation or working round goes at a time; a start while one is going says what is going, and a start while the agent isn't running says so and leaves the dispatch stopped with that reason. On the Scoreboard, choose a labeled set, all its claims or the five tiny ones, and the claim agents at once, and press Start an evaluation. `uv run -m agent CLM-1001` works one claim with no run, printing its report line. All three use the real model through OpenRouter and save the claim graph's progress in Supabase.
- The agent's optional settings, in the shell or `.env`: `UNDERCOVER_GATEWAY_URL` sends the claim agents' tools and payments through that AgentCore Gateway, `UNDERCOVER_CONTEXT` points the direct route at another context layer, and `UNDERCOVER_MEMORY_ID` gives them that AgentCore Memory. With either AWS setting, the agent uses the AWS CLI's credentials and region. `labs/week3day3.ipynb` deploys the app and the context layer, creates the Gateway and the memory, and writes the two settings into `.env`.
- On the Improvement page, a handler who can sign off over the limit presses Start a round. The round runs the first evaluations the current version needs, then the improver proposes a change, which shows with its diff and reason for the handler to approve, after confirming, or reject with a reason. An approved change is evaluated and kept or rolled back by the business's rule, then the improver proposes a new recipe for the next round. Stop the round ends it at any point. Every round costs at most the spending limit in the settings, $0.50 to start with.
- A payout over the limit waits for a senior handler on its claim page. Sign off pays it at once; the claim graph paused when the payout was held, and the sign-off asks the agent to resume it, which ends the agent's work on the claim and saves it to memory when memory is on. Send back, with a note of up to 1,000 characters, clears the decision and asks the agent to resume the claim with the note, or leaves it for the next dispatch when the agent doesn't get it; the agent decides again.

## Built

- `backend/`: the database is seeded from `data/`, with the plans and the two documents from `context/`, and created on startup when it has no tables. Only seeding reads `data/evals/`. A test checks that every operation follows the API rules. `main.py` holds the app and the claim, document and handler operations; `runs.py` is an `APIRouter` with every operation under `/api/runs`, `/api/dispatches` and `/api/evaluations`; `configuration.py` is an `APIRouter` with the claim agent's versions; `improvement.py` is an `APIRouter` with the rounds of the improver, the agent's operations under `/api/rounds` and the dashboard's under `/api/improvement`. They share the `Database` and `SignedIn` dependencies in `dependencies.py`, `to_claim()` and `to_summary()` in `views.py`, finding a run or a version and the not-found messages in `lookups.py`, reading runs in `scoreboard.py` and `now()` in `database.py`, and no router uses another's helpers. Claim and run statuses, decisions, run kinds and labeled sets are `StrEnum`s in `models.py`.
  - On AWS Lambda: `handler` at the end of `backend/main.py` is the app through Mangum, with the startup hook off, so nothing seeds the database there. With `AWS_LAMBDA_FUNCTION_NAME` set, `engine_for` opens Postgres with a connection for each request and none kept (`NullPool`) and prepared statements off (`prepare_threshold=None`), for Supabase's transaction pooler on port 6543. `backend/dashboard.py` serves `dashboard/dist` through a Starlette `StaticFiles` that gives `index.html` for any page it has no file for, on a `Mount` after every route that takes no path under `/api/`, and none while the dashboard isn't built: the API, its wrong methods, trailing slashes and unknown paths, and `/docs`, answer as they always have. `npm run check:server` imports the backend in a temporary environment with only the `server` dependency group, the packages the deployment installs.
  - Database: SQLAlchemy Core, with the tables and every query written once in `backend/database.py` for both databases. With `DATABASE_URL` set, it is the Supabase Postgres database, through psycopg and the session pooler, with every table in the `undercover` schema (`search_path` is set on each connection, in place of any `options` in the URL and keeping its other settings, such as `sslmode`) and a pool of at most 4 connections, waiting up to two minutes for one. Otherwise it is SQLite at `undercover.db` or the path in `UNDERCOVER_DB`, with a connection per request. Each request runs in one transaction, committed before the response is sent. The tests and the end-to-end tests always use SQLite and never touch the network.
  - Sign-in: `backend/auth.py` checks a Supabase access token with PyJWT's `PyJWKClient` against the project's public keys at `VITE_SUPABASE_URL`, with the audience `authenticated` and 30 seconds of clock leeway, and returns its email; nothing else reads the address. `SignedIn` in `dependencies.py` finds the handler by that email (401 without a valid token, 403 for an email that isn't a handler's). `get_signed_in_handler` (`GET /api/me`) returns the handler with their email and whether they can sign off over the limit. Every route the dashboard alone calls needs a signed-in handler. Seeding stores each handler's email, and only Dana Whitfield can sign off over the limit.
  - The agent's API key: `backend/api_key.py` compares the key a request sends in `X-API-Key` with `UNDERCOVER_API_KEY`, as bytes, with `secrets.compare_digest`; with no key set nothing matches. `dependencies.py` puts one gate on every route but `health`: `AgentKey` on the operations only the agent's side calls (the claim workflow, the versions it reads, the documents, and everything the service records about runs and rounds, including a round or a review for a handler), `HandlerOrAgent` on the four reads both use (`list_claims`, `get_claim`, `get_policy`, `get_claim_history`), on `get_run`, which the agent and the Copilot's wait both read, and on `get_agent_api`, and a signed-in handler on everything else. The key never stands in for a handler. A test checks that the four lists of operations cover the app exactly once and that each operation's OpenAPI security matches its gate.
  - Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `get_settings`, `list_steps`, `get_current_version`, `get_version`, `get_screening`, `get_configuration`, `get_version_details`, `get_latest_dispatch`, `list_evaluations`, `get_evaluation`, `get_agent_api`.
  - Settings: `settings` keeps the platform's settings as a history, one row per change with who made it and when; the newest row is in force. Seeding makes row 1 with the approval limit from `data/company.json` and the rest from `data/improvement.json`: the objectives on the held-out set, the noise and the tolerance, the spending limit for each round and the claim agents at once in the improver's evaluations. `data/models.json` gives the models the claim agent may use, with their reasoning efforts and prices, seeded into `models_allowed` (with `MODEL_NAME` set, that model alone at `default` and a price of 0). `get_settings` returns the settings in force, every change and the models allowed; `change_settings` (`PUT /api/settings`) records a new row, and only a handler who can sign off payouts over the limit may use it (`senior(action)` in `dependencies.py`, which names the action in its 403).
  - The judge: `backend/judge.py` is the one module that calls Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions endpoint with the `openrouter` package, at `JUDGE_URL` or `https://openrouter.ai`, with the lab's rubric and three questions, a 10 second timeout and no retries. It grades the agent's reason and section against the handler's reason and reference, which seeding stores in `handler_decisions`; the score is Jev's score from 0 to 3, the letter the likeliest level, and the two checks, same grounds and same section, are kept as probabilities. `finish_run` grades an evaluation's copies in parallel, one thread each, before it finishes: an undecided copy gets an F without asking the judge, and a copy the judge can't grade is recorded with no grade and logged. `grades` holds each copy's grade and the judge's cost. An evaluation's grade averages its graded copies, and its judge cost is apart from its model cost. With `MODEL_NAME` set there's no judge, and nothing is graded.
  - The claim agent's own API: `get_agent_api` (`GET /api/agent/openapi.json`, for the key or a signed-in handler) returns the OpenAPI document of the six operations the claim agent's tools and its payment call, `get_claim`, `get_policy`, `get_claim_history`, `calculate_payout`, `record_decision` (whose body requires `decided_by`) and `pay_claim`, built in `backend/agent_api.py` with FastAPI's `get_openapi` from the app's own routes, with their operation ids and one-line descriptions. It has no `servers`, which the deployment adds, and no security schemes, which a Gateway's OpenAPI target doesn't support; the Gateway's credential provider sends the key. The payment's body keeps `amount`, which the Gateway's Policy reads.
  - Payouts: `calculate_payout` works out the payout on a claim with UnderCover's payout rules in `backend/payout.py`, brought in from `labs/week2day1_payout.py`, and keeps it in `calculations` for the claim's current attempt, on its thread, each calculation replacing the last (`backend/calculation.py`); it refuses a claim that isn't in progress with a 409. Seeding stores the plans from `context/plans.yaml` in `payout_rules`, and the approval limit comes from the settings in force, so the rules read nothing from `data/`. A new approval limit applies to the decisions recorded after it. Every input of the operation is required, including each field of a line.
  - Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `hold_payment`, `sign_off_claim`, `send_back_claim`, `take_claim`, `record_claim_heartbeat`, `fail_claim`, `record_model_call`, `record_work_time`. `record_step` takes each step's `sources`, the context files a lookup came from, and none for any other step; the kinds are `screening`, `tool_call`, `tool_result`, `message`, `lookup`, `memory_search`, `memory_save`, `refusal` and `error`, and the app records a `sent_back` step itself.
  - Sending back: `send_back_claim` (`POST /api/claims/{claim_id}/send-back`, body `{note}`, for a handler who can sign off over the limit) moves a claim waiting for sign-off to sent back with the same conditional update as the sign-off, so only one of the two goes through, and refuses a copy, a claim not waiting for sign-off (409), a blank note or one over 1,000 characters (422). It keeps the decision with its calculation, the note, who sent it back and when in `sent_back_decisions` (`backend/sent_back.py`), deletes the decision and the claim's calculation, records "Sent back by Dana Whitfield: ..." as a `sent_back` step, commits, and asks the agent to resume the claim, answering with the claim whatever happens to that call. A claim in full has its `sent_back_decisions`, oldest first. `take_claim` (`POST /api/claims/{claim_id}/take`, body `{run_id}`, for the agent's key) moves a sent-back claim to in progress, on the same thread and attempt, for the first caller only, and any other gets a 409; with no run it is a resume, which sets `resume_heard_at`, as each `record_claim_heartbeat` does. A claim's line in the queue says `resuming` while it is in progress and the agent spoke of its resume in the last five minutes (`backend/agent_work.py`). A dispatch's summary counts a sent-back claim as unfinished.
  - A complete decision record (claims manual section 14): `record_decision` takes `decided_by` and checks, in order, the request before it reads the claim (a blank reason, section or maker, an approval paying nothing, a decline or referral paying something, each a 422 whose `detail` names section 14), the claim as before, then for an approval the calculation on file for this attempt and its payout (`backend/records.py`). The record holds the calculation's lines and payout, `decided_by`, `decided_at` and `manual_version`, the claims manual's version from the documents table, and a sign-off adds who signed off and when. `hold_payment` (`POST /api/claims/{claim_id}/hold`, for the agent's key, off the Gateway) moves an approved, unpaid claim in progress to waiting for sign-off with the Gateway's reason as `gateway_refusal`; a repeat returns the claim.
  - Cost and time: `record_model_call` records one model call's input and output tokens and its cost in US dollars on a started claim, in `model_calls`, and `record_work_time` one spell of the agent's work, in `work_times`, with its start worked out from the time it's recorded less its seconds. Each has the claim's thread and the run it happened in, or none.
  - Claims: a claim moves from waiting to in progress. A decline or a referral is then decided. An approval stays in progress until `pay_claim` pays it, which decides it, or moves to waiting for sign-off when its payout is over the approval limit in force. `pay_claim` first refuses any amount over the approval limit in force with a 403, "A payout over $1,000.00 needs a handler's sign-off", before it reads the claim, so an over-limit payment gets the same answer on any claim; then it refuses a payout held for sign-off with the same message, naming the limit it was held under. A sign-off moves the claim from waiting for sign-off to decided with a conditional update, so of two sign-offs at the same moment only one goes through, records the signed-in handler and the time on the decision and pays the approved payout, commits, and then asks the agent to resume the claim (`agent_service.resume_claim`), answering with the paid claim whatever happens to that call and logging a warning when it fails. The `Database` dependency opens one connection for a request and commits at its end, and a route can commit sooner with `db.commit()`, as the sign-off does before it calls the agent. The payment shows who signed off and when. A repeat of the decision or payment already recorded returns the claim, and a different one is refused with a 409, so a step that runs again after a restart does no harm. `pay_claim` returns the claim. Each start counts as an attempt. `fail_claim` records the reason as an `error` step and puts the claim back to waiting, or after its second attempt leaves it `left_for_handler`; it refuses a claim that has a decision.
  - Starting: `start_dispatch` (`POST /api/dispatches`, body `{agents}`) and `start_evaluation` create the run, with an evaluation's copies, through `backend/agent_work.py`: the lock (an update of the one row in `locks`, the transaction's first write), quiet work marked stopped (a run, or a round with its running evaluation, whose `heard_at` is more than five minutes old, "The agent stopped answering"; a round's evaluation is never stopped on its own), a 409 naming the work going ("A dispatch is running", "An evaluation is running", "Round 3 is running"), the run, `heard_at`, a commit, then `work_run` for the agent, and 202. When the agent didn't take the work the run is stopped with the reason and the undo committed before the refusal; a timeout changes nothing, so the run stays running until it goes quiet. The agent's refusal is a 409 with its reason, an agent that can't be reached a 503 "The agent's service isn't running", an error answer a 502 "The agent couldn't take the work: ...", and a timeout or a cut-off answer a 503 telling the handler to reload. `agent_service.py` sends each operation's payload to `/invocations` at `UNDERCOVER_AGENT` or `http://127.0.0.1:8080` with the key as `Authorization: Bearer <key>`, or, when `UNDERCOVER_AGENT_RUNTIME` names the agent's runtime, with boto3's `invoke_agent_runtime`, a new session each call, one attempt, 2 seconds to connect and 15 to read, through `runtime_calls.py`; it reads the answer's `statusCode` before its body, and an answer that is neither an acceptance nor a refusal is an error answer.
  - Runs: a run is a dispatch or an evaluation, with a number, its N claim agents at once, the version of the claim agent it used with that version's model and reasoning effort, which the backend records when the run is created, a status (running, finished or stopped), its start and finish, and its claims in order in `run_claims`. A handler's start creates them; the agent reads one with `get_run`, records its claims and finishes it with `record_run_claims` and `finish_run`, tells the app it's still working with `record_run_heartbeat`, and stops one whose work failed with `fail_run`, under `/api/runs`. A stopped run keeps why in `stopped_because`: the agent's refusal or why it couldn't be reached, the error from `fail_run`, "The agent stopped answering", its round's reason, or the spending limit that cut it short. `finish_run` on a run stopped meanwhile answers with it, still stopped and with nothing graded. A run in a response has each claim's line from the queue with its start, seconds and model cost in the run, the run's model cost, and its seconds once it finishes. `finish_run` builds a dispatch's summary from its claims as they stand, counting each claim once: approved, declined and referred, the payouts waiting for a sign-off (counted as approved), the claims left for a handler, and the unfinished ones, in progress or back in the queue, for the next dispatch.
  - Evaluations: `start_evaluation` creates an evaluation of the evaluation set (the 25 claims in `data/claims.json`) or the held-out set (in `held_out_claims`), whole or its five `tiny` claims, and makes a waiting copy of each claim, oldest submitted first, with an id like `CLM-1104-E7` written into its record too. Copies are rows in `claims` with `evaluation_id` and `copy_of`, so every claim operation works on them, but `list_claims` leaves them out and `sign_off_claim` refuses one with a 409. `list_evaluations` and `get_evaluation` score each evaluation from its copies as they stand and the handlers' decisions in `handler_decisions`, with the lab's measures in `backend/scoring.py`: decision accuracy, accuracy (a payout within a dollar), the cost of mistakes ($1,500 a wrongful decline, a wrongful approval's payout, $50 a needless referral, the difference on a right approval), the straight-through rate, model cost and time per claim, and the run's time. A copy the agent didn't decide counts as a referral. No response the agent reads holds anything from `handler_decisions`.
  - Documents: seeding stores the policy wording and the claims manual from `context/` in a `documents` table with their titles and versions (`backend/context_files.py`, which only seeding calls), without their front matter. The backend lists their numbered sections at the end of the claim agent's instructions and gives the manual's version to each decision; the context layer serves the documents to the agent.
  - The configuration in versions: the claim agent's instructions, model and reasoning effort are kept in `versions`, each with what it changed from the version it was based on, its reason, who proposed and approved it and when, and its verdict. Version 1 is seeded from `backend/instructions/claim.md`, which gives the claim agent its goal, what it has to work from and what done looks like, on `openai/gpt-6-luna` with no reasoning (`none`), so a higher reasoning effort is an improvement a round can find. With `MODEL_NAME` set when seeding, version 1 is that model at `default`, with no reasoning effort sent; `backend/free_models.py` is the only code that reads `MODEL_NAME`, so set it in `.env` before `npm run seed`. The current version is the newest kept one. `get_current_version` and `get_version`, which the claim agent's client reads, hold the number, the instructions followed by the contents of the wording and the manual, the model and the reasoning effort, and no scores. `get_configuration` and `get_version_details` add each version's status, its diff from the version it was based on (`backend/diffs.py`, from `difflib.unified_diff` with two lines of context), and its scores: the averages of the finished whole-set evaluations rounds ran on it, empty until rounds exist.
  - Rounds of the improver: `rounds` records each round with who started it, the settings, recipe and version in force, the improver's model (`openai/gpt-6.1-sol` at medium, or the model in `MODEL_NAME` at `default`), its thread and the first evaluations the current version still needs, one on the evaluation set and two on the held-out set. One round is open at a time. `proposals` holds the improver's proposals, a change (instructions, model, reasoning effort, reason) or a recipe, and each one's review; `recipes` holds the recipe's versions, seeded from `backend/instructions/recipe.md`, and `improver_calls` the improver's model calls. `round_state.py` works out where a round has got to from these records (`first_evaluations`, `improving`, `change_waiting`, `evaluating`, `verdict`, `recipe_waiting`), and stopping a round stops its running evaluation with the round's reason and rolls back a version it hasn't given a verdict. A proposal changes nothing, a change to a model outside the models allowed is refused as it's proposed, and a round has one approved change at most: once a handler who can sign off over the limit approves it, `create_version` makes it a version under test, refusing a model outside the models allowed with a 422. The dashboard's `approve_proposal` and `reject_proposal` name the proposal, and refuse with a 409 one that isn't waiting. `create_round_evaluation` makes a round's next evaluation at its agents at once, choosing its set itself: its starting version on the sets of its first evaluations, then its version under test once on the evaluation set and twice on the held-out set until the verdict, so a version's scores never change after it, refusing a version's first one when the three could cost more than what's left of the limit, estimated from the highest cost per claim seen on the version's model or, with none, on another model scaled by its prices (`spending.py`). A round's cost is its improver calls, its evaluations' model calls and the judge; once it reaches the limit, `start_claim` refuses a new claim in its evaluations and the evaluation finishes stopped, which stops a round still in its first evaluations. `record_verdict` keeps or rolls back the version by the rule in `verdict.py`, on the averages of its held-out evaluations against the current version's. `get_improver_view` gives the improver the current version, its scores, the evaluation set's wrong claims and the five right ones explained least well beside the handlers' reasons, the earlier rounds, the settings, the rule, the spending and the models allowed, and nothing from the held-out set but scores. `get_improvement` gives the dashboard the open or newest round with its stage, progress, proposal waiting and diff, evaluations and cost, every round, the versions tried and the recipes. `start_round` and `stop_round` need a handler who can sign off over the limit, and `start_round` creates the round, and `approve_proposal` and `reject_proposal` record the review with who, when and the reason, through `agent_work.py` as a start does, then ask the agent to `work_round` or `carry_round_on`; when the agent didn't take it, a new round is stopped with the reason and a review is cleared, so the proposal waits for a handler again. ## Known gaps

- A sign-off whose resume fails, because the call to the agent fails or the resumed work does, isn't remembered: the claim is paid, but the agent's work on it isn't finished, so it isn't saved to memory.
- A resume that fails, such as on a rate limit, isn't tried again: it's logged, and the next dispatch carries the claim on once the resume has been quiet for five minutes.
- A request that asks the agent for something, such as a sign-off or a start, holds its database connection until the agent answers, up to 10 seconds, while the agent may call the app back before it answers. With the laptop's four connections, several such requests at once while a dispatch is busy could wait out the 10 seconds; nobody has seen it happen.
- A claim with a decision but nothing saved on its thread, which only happens when someone approves a claim through the API by hand, can't be carried on: each run logs the error and leaves it in progress.
- If two processes carry the same claim on at the same moment, which the harness can't rule out, the backend still decides and pays it once. The second process's decision or payment, arriving while the first is being saved, is refused with an error, and that process logs it.
- A handler signs off a held payout or sends it back to the agent; declining one outright comes later.
- Work the app marks stopped as quiet isn't told: an agent still alive whose heartbeats were failing keeps working, and the next dispatch can pick up the same claims in progress. The backend still decides and pays each claim once, as when two processes carry the same claim on.
- A sign-off on a claim that never paused, because its process stopped after the decision and before the pause, stands and is paid, but isn't remembered either.
- A sent-back claim whose resumed work fails before a new decision goes back to the queue, and the dispatch works it afresh, as a new attempt on a new thread, without the note.
- A claim stopped between its approval's tool call and the save of that step, then sent back, carries on from that tool call without the note: the app refuses the old approval, since the send back cleared its calculation, and the model works on from the refusal.
- The dispatcher's worker re-raises a rate limit or a timeout until its last try, rather than using LangGraph's `error_handler`: in LangGraph 1.2.12 a handled error is still raised from `invoke` when the worker runs beside others. A test records this, so a release that fixes it shows up.
- `uv run -m agent CLM-1001` beside a dispatch can work the same claim at the same moment; the backend still decides and pays it once.
- At 25 claim agents at once each step outside the model takes about 2.6 times as long as at 3 (0.37 against 0.14 seconds), most likely from waiting on the 4 connections a process to Supabase (see the live run below). The model itself is no slower.
- GPT-6 Luna sometimes ends its turn with a message instead of recording a decision: 4 times in the live runs below. The harness fails that attempt and the dispatch works the claim once more. A claim this happens to twice is left for a handler, as CLM-1017-E3 was.
- Langfuse loses the traces of claims stopped by `kill -9` before the service's client sent them.
- An improver call answered just as a handler stops the round isn't recorded, since a stopped round records nothing more, so the round's cost can be short by that one call. The stretch ends there.
- `/docs` and `/openapi.json` stay open. They describe the routes and grant nothing.
- Two senior handlers saving the settings at the same moment: the later save is built on the settings as its page loaded them, so it can undo the other's change.
- In a production build the page can paint once before `theme.ts` sets a saved appearance that differs from the computer's.
- A refused sign-off says the approval limit in force now, not the one the payout was held under, if they differ.
- An approval within the limit that isn't paid yet, because its payment failed or the agent stopped just before paying, can't be paid if the limit is lowered below it meanwhile: `pay_claim` checks the limit in force before it reads the claim, as the Gateway's Policy will, and only a payout held when it was decided can be signed off. It stays in progress for a handler. A test records this.
- The Improvement page re-scores every round's evaluations on each two-second refresh, which grows with the rounds run.
- A claim's decision arriving moves the agent's steps below it down once, by the decision's height: it's new content, and keeping room for a decision would leave a large empty panel on every claim. While an evaluation runs, a copy's own cost and time grow in place in their right-aligned cells.
- Rounds can't run on free models, which allow fewer requests in a day than a round needs; students on free models build and test everything.
- Stopping `npm run dev` with SIGTERM twice left a uvicorn reloader holding its port with no worker; `kill -9` on it cleared the port.
- The data dictionary in `context/` doesn't describe a decision's `gateway_refusal`; it's data governance's file, so it's left as it is.
- AgentCore turns a saved claim into memories in the background, about 90 seconds after the save in our team's experiment, so a customer's next claim worked straight away may not find the first.
- A crash after a claim is decided or held and before `remember` finishes loses that claim's memory, or keeps only its first event: the dispatcher only carries on claims in progress, so nothing runs `remember` again. An approval stopped before its payment is carried on, paid and remembered once.
- `uv run -m agent` on an evaluation's copy, which nothing does, would work it with the memory: memory follows the kind of run, and a claim worked on the command line has none.
- The live runs used the direct route with memory off; the Gateway's names, its refusals and the memory are covered by the tests with stand-ins, and by the deployment notebook.
- A Copilot turn that works past its sign-in's hour, such as two long waits in one turn, is refused by the app partway. With the sign-in gone, the Copilot can't tell the app either, so the turn stops there, its card still spinning, and shows as working until it reads as stopped, 20 minutes after it started. The sidebar renews a sign-in with less than 20 minutes left before it sends, which covers one 15-minute wait.
- A Copilot turn stopped partway, such as when its process dies, shows as stopped only 20 minutes after its start or its confirmation's answer.
- The Copilot's records take the handler's sign-in, so a handler could write to their own conversation's records through the API, adding cards or an answer. Nothing in them pays or decides: the sign-off and every other action go through the app's own operations and rules.
- Explaining a claim's decision, the Copilot on GPT-6 Luna at `low` reads the claim, the claim agent's steps, the policy and the settings, and quotes the sections the agent cited, but in the live run never read the context layer itself unless asked to check a section, though its instructions set that goal, first as what to draw on and then as when an explanation is done. Making it hold would take code, such as a claim read that brings the sections the decision cites from the context layer.
- The 15-second read on the Runtime route hasn't been measured live. A cold Copilot session that takes longer to fetch its credentials, open its pool and check the sign-in and the turn would give the handler a "may have started" 503, though the turn would go on.
- The Copilot's route can reach the app's tools as well as the context layer's, and the app's act as the agent; only the Copilot's tools, which take the context layer's alone, keep it from them. On Runtime, the Gateway's Policy should keep the Copilot's role to the `undercover-context___` tools.
- A held decision that changes between the handler's answer to a confirmation and the Copilot's sign-off, a few seconds later, is signed off as it then stands, as on the claim's page between loading it and pressing Sign off.
- A first message the Copilot doesn't take leaves its conversation, with the turn failed and the reason, in the earlier conversations, while the sidebar shows the reason under the box and stays on the greeting.
- AgentCore turns a conversation into the handler's memories in the background, about a minute and a half after the save, so a new conversation straight away may not find what the handler just said.
- A Copilot that stops after saving its pause and before telling the app leaves the graph waiting for an answer while the app shows the turn working, with no confirmation card, until it shows as stopped.
- A Copilot that stops after saving its result and before telling the app leaves the sidebar without the answer, or a confirmation's outcome, that the saved graph already has, though a sign-off may have paid or the memory saved. The turn shows as working and then stopped, and nothing puts the two together; a confirmation card whose sign-off began says its outcome is not known, and the claim's page says whether it was paid.

## Supabase

The backend's tables and the checkpointer's are in the `undercover` schema. Row Level Security is off on them, and Supabase's table listing warns about that, but the schema isn't exposed through Supabase's Data API: the `anon`, `authenticated` and `service_role` roles have no access to it, and Supabase's security advisor reports nothing. The backend and the agent connect as `postgres`, the tables' owner.

## Review of the harness

On September 30, 2026, the head of engineering's review (`docs/HUMAN_REVIEW_HARNESS.md`) found that the harness was unfit for a PR:
- The agent had more than 20 hard-coded backend URLs and two ways of calling the backend.
- `queue.py` reached into `main.py`.
- The tools were spread across files, and state was passed through closures instead of LangChain's `context_schema`.
- The instructions were step-by-step scripts.

The agent was rebuilt as `api.py`, `tools.py` and `harness.py`, and the instructions were rewritten as goals. Fresh reviewers then went through the backend, the dashboard and the tests, and their fixes are in the same change.

These problems passed every check. Each phase was built, checked against its criteria and committed, and nobody read the code the way a reviewer reads a PR. `docs/CODE_STANDARDS.md` now sets the structural rules the review found broken. `docs/PROCESS.md` now requires a review by a fresh subagent before every commit, and a design in every plan.
