# Status

The claims pilot in `docs/PLAN.md`, the harness in `docs/PLAN_HARNESS.md` and durable state in `docs/PLAN_DURABLE.md` are built: all six phases of each are done. The swarm and the scoreboard in `docs/PLAN_SWARM.md` are built too: all six phases are done. The improver and sign-in in `docs/PLAN_IMPROVE.md` are built: all seven phases are done: handlers sign in, the claim agent's configuration is kept in versions, the platform's settings are on a Settings page, a judge grades each evaluated claim's explanation, and a senior handler runs rounds of the improver on the Improvement page, approving or rejecting each change and recipe it proposes. A dispatcher with no model works the queue with up to 25 claim agents at once, on GPT-6 Luna by default, recording the cost and time of every claim, and a Scoreboard scores evaluations on copies of the labeled claims. The security changes in `docs/PLAN_SECURE.md` are built: all five phases are done: the agent's side identifies itself to the backend with an API key, a second model checks each claim for instructions hidden in it before the claim agent's model sees it, the backend serves the claim agent's own API document for the Gateway, a handler's sign-off pays a held payout, and the backend and the dashboard are ready for AWS Lambda. The context layer, memory and the Gateway in `docs/PLAN_CONTEXT.md` are built: all six phases are done. The claim agent works from three sources of data: the context layer in `context/`, an MCP server of its own with seven read-only lookups over data governance's files, each answer naming its files and their sources; its memory of each customer in AgentCore Memory, when `UNDERCOVER_MEMORY_ID` is set and outside evaluations; and the app's records. Its tools and its payment go through the AgentCore Gateway when `UNDERCOVER_GATEWAY_URL` is set, signed with the AWS CLI's credentials, or straight to the app and the context layer otherwise, taking no ids from the model, and a payment the Gateway refuses waits for a handler's sign-off. Seeding loads the plans and the two documents from `context/`, and the app no longer serves the documents. Every decision record meets claims manual section 14, with its calculation, who or what made it, when, and the manual's version. The claim page shows every lookup and where it came from, every memory search and save, every refusal, a Context used panel and the whole decision record.

## Running it

- After pulling the security changes, reseed with `npm run seed`: a claim signed off but not yet paid under the old flow can't be paid any more.
- `.env` needs `UNDERCOVER_API_KEY`, the agent's API key, a random value of at least 32 characters such as one from `secrets.token_urlsafe(32)`; the agent's service doesn't start without it.
- After pulling the context layer, reseed with `npm run seed`: the documents table has a version, and the decisions and steps have new columns.
- `npm run dev` starts the backend on port 8000, the agent's service on port 8002, the context layer on port 8006 (`uv run -m context`, at http://127.0.0.1:8006/mcp) and the dashboard on http://localhost:5173. It passes `.env` to the backend and the agent's service, so it needs a `.env`. With `DATABASE_URL` there the backend uses Supabase; the agent's service and `uv run -m agent` always need it, since they save the claim graph's progress there.
- `npm run seed` rebuilds the database `npm run dev` uses from `data/`, with the plans and the two documents from `context/`, putting every claim back in the queue and emptying the dispatches and evaluations. The queue's 26 claims include the security team's CLM-1901 from `data/security/`, whose handler's decision is never seeded. It also stores the held-out claims and the handlers' decisions on both labeled sets from `data/evals/`, which nothing else reads. It drops the old `todos` table first when it's there. `uv run -m backend.seed` alone never reads `.env` and rebuilds the SQLite file `undercover.db`, as the end-to-end tests do. The backend only seeds a database with no tables, so reseed after pulling a change to the tables.
- If you're on a free model, set `MODEL_NAME` in `.env` before `npm run seed`: seeding chooses version 1 of the claim agent and the models allowed from it.
- Every page needs a signed-in handler. Sign in on `/sign-in` with a handler's email from `data/handlers.json` and the password set for them in Supabase Auth (`HANDLER_PASSWORD` in `.env`). There's no sign-up. Dana Whitfield is the only handler who can sign off payouts over the limit.
- `npm run build` builds the dashboard into `dashboard/dist`, with the Supabase address and publishable key from `.env`. When the folder exists, the backend serves it at `/` beside the API, so `uv run --env-file .env -m uvicorn backend.main:app` alone serves the whole app at http://127.0.0.1:8000; `npm run dev` is unchanged. `docs/TECH_STACK.md` describes the deployment.
- On the queue page, choose the claim agents at once, from 1 to 25, and press Start a dispatch. The backend asks the agent's service, which works every claim in progress and every waiting claim with up to N claim agents at once. Only one dispatch, evaluation or stretch of a round runs at a time, and a start while the service isn't running says so. On the Scoreboard, choose a labeled set, all its claims or the five tiny ones, and the claim agents at once, and press Start an evaluation. `uv run -m agent CLM-1001` works one claim with no run, printing its report line. All three use the real model through OpenRouter and save the claim graph's progress in Supabase.
- The agent's optional settings, in the shell or `.env`: `UNDERCOVER_GATEWAY_URL` sends the claim agents' tools and payments through that AgentCore Gateway, `UNDERCOVER_CONTEXT` points the direct route at another context layer, and `UNDERCOVER_MEMORY_ID` gives them that AgentCore Memory. With either AWS setting, the agent uses the AWS CLI's credentials and region. `labs/week3day3.ipynb` deploys the app and the context layer, creates the Gateway and the memory, and writes the two settings into `.env`.
- On the Improvement page, a handler who can sign off over the limit presses Start a round. The round runs the first evaluations the current version needs, then the improver proposes a change, which shows with its diff and reason for the handler to approve, after confirming, or reject with a reason. An approved change is evaluated and kept or rolled back by the business's rule, then the improver proposes a new recipe for the next round. Stop the round ends it at any point. Every round costs at most the spending limit in the settings, $0.50 to start with.
- A payout over the limit waits for a handler to sign it off on its claim page, and the sign-off pays it at once. The claim agent's work on the claim ended when it was held.

## Built

- `backend/`: the database is seeded from `data/`, with the plans and the two documents from `context/`, and created on startup when it has no tables. Only seeding reads `data/evals/`. A test checks that every operation follows the API rules. `main.py` holds the app and the claim, document and handler operations; `runs.py` is an `APIRouter` with every operation under `/api/runs`, `/api/dispatches` and `/api/evaluations`; `configuration.py` is an `APIRouter` with the claim agent's versions; `improvement.py` is an `APIRouter` with the rounds of the improver, the agent's service's operations under `/api/rounds` and the dashboard's under `/api/improvement`. They share the `Database` and `SignedIn` dependencies in `dependencies.py`, `to_claim()` and `to_summary()` in `views.py`, finding a run or a version and the not-found messages in `lookups.py`, reading runs in `scoreboard.py` and `now()` in `database.py`, and no router uses another's helpers. Claim and run statuses, decisions, run kinds and labeled sets are `StrEnum`s in `models.py`.
  - On AWS Lambda: `handler` at the end of `backend/main.py` is the app through Mangum, with the startup hook off, so nothing seeds the database there. With `AWS_LAMBDA_FUNCTION_NAME` set, `engine_for` opens Postgres with a connection for each request and none kept (`NullPool`) and prepared statements off (`prepare_threshold=None`), for Supabase's transaction pooler on port 6543. `backend/dashboard.py` serves `dashboard/dist` through a Starlette `StaticFiles` that gives `index.html` for any page it has no file for, on a `Mount` after every route that takes no path under `/api/`, and none while the dashboard isn't built: the API, its wrong methods, trailing slashes and unknown paths, and `/docs`, answer as they always have. `npm run check:server` imports the backend in a temporary environment with only the `server` dependency group, the packages the deployment installs.
  - Database: SQLAlchemy Core, with the tables and every query written once in `backend/database.py` for both databases. With `DATABASE_URL` set, it is the Supabase Postgres database, through psycopg and the session pooler, with every table in the `undercover` schema (`search_path` is set on each connection, in place of any `options` in the URL and keeping its other settings, such as `sslmode`) and a pool of at most 4 connections, waiting up to two minutes for one. Otherwise it is SQLite at `undercover.db` or the path in `UNDERCOVER_DB`, with a connection per request. Each request runs in one transaction, committed before the response is sent. The tests and the end-to-end tests always use SQLite and never touch the network.
  - Sign-in: `backend/auth.py` checks a Supabase access token with PyJWT's `PyJWKClient` against the project's public keys at `VITE_SUPABASE_URL`, with the audience `authenticated` and 30 seconds of clock leeway, and returns its email; nothing else reads the address. `SignedIn` in `dependencies.py` finds the handler by that email (401 without a valid token, 403 for an email that isn't a handler's). `get_signed_in_handler` (`GET /api/me`) returns the handler with their email and whether they can sign off over the limit. Every route the dashboard alone calls needs a signed-in handler. Seeding stores each handler's email, and only Dana Whitfield can sign off over the limit.
  - The agent's API key: `backend/api_key.py` compares the key a request sends in `X-API-Key` with `UNDERCOVER_API_KEY`, as bytes, with `secrets.compare_digest`; with no key set nothing matches. `dependencies.py` puts one gate on every route but `health`: `AgentKey` on the operations only the agent's side calls (the claim workflow, the versions it reads, the documents, and everything the service records about runs and rounds, including a round or a review for a handler), `HandlerOrAgent` on the four reads both use (`list_claims`, `get_claim`, `get_policy`, `get_claim_history`) and on `get_agent_api`, and a signed-in handler on everything else. The key never stands in for a handler. A test checks that the four lists of operations cover the app exactly once and that each operation's OpenAPI security matches its gate.
  - Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `get_settings`, `list_steps`, `get_current_version`, `get_version`, `get_screening`, `get_configuration`, `get_version_details`, `get_latest_dispatch`, `list_evaluations`, `get_evaluation`, `get_agent_api`.
  - Settings: `settings` keeps the platform's settings as a history, one row per change with who made it and when; the newest row is in force. Seeding makes row 1 with the approval limit from `data/company.json` and the rest from `data/improvement.json`: the objectives on the held-out set, the noise and the tolerance, the spending limit for each round and the claim agents at once in the improver's evaluations. `data/models.json` gives the models the claim agent may use, with their reasoning efforts and prices, seeded into `models_allowed` (with `MODEL_NAME` set, that model alone at `default` and a price of 0). `get_settings` returns the settings in force, every change and the models allowed; `change_settings` (`PUT /api/settings`) records a new row, and only a handler who can sign off payouts over the limit may use it (`senior(action)` in `dependencies.py`, which names the action in its 403).
  - The judge: `backend/judge.py` is the one module that calls Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions endpoint with the `openrouter` package, at `JUDGE_URL` or `https://openrouter.ai`, with the lab's rubric and three questions, a 10 second timeout and no retries. It grades the agent's reason and section against the handler's reason and reference, which seeding stores in `handler_decisions`; the score is Jev's score from 0 to 3, the letter the likeliest level, and the two checks, same grounds and same section, are kept as probabilities. `finish_run` grades an evaluation's copies in parallel, one thread each, before it finishes: an undecided copy gets an F without asking the judge, and a copy the judge can't grade is recorded with no grade and logged. `grades` holds each copy's grade and the judge's cost. An evaluation's grade averages its graded copies, and its judge cost is apart from its model cost. With `MODEL_NAME` set there's no judge, and nothing is graded.
  - The claim agent's own API: `get_agent_api` (`GET /api/agent/openapi.json`, for the key or a signed-in handler) returns the OpenAPI document of the six operations the claim agent's tools and its payment call, `get_claim`, `get_policy`, `get_claim_history`, `calculate_payout`, `record_decision` (whose body requires `decided_by`) and `pay_claim`, built in `backend/agent_api.py` with FastAPI's `get_openapi` from the app's own routes, with their operation ids and one-line descriptions. It has no `servers`, which the deployment adds, and no security schemes, which a Gateway's OpenAPI target doesn't support; the Gateway's credential provider sends the key. The payment's body keeps `amount`, which the Gateway's Policy reads.
  - Payouts: `calculate_payout` works out the payout on a claim with UnderCover's payout rules in `backend/payout.py`, brought in from `labs/week2day1_payout.py`, and keeps it in `calculations` for the claim's current attempt, on its thread, each calculation replacing the last (`backend/calculation.py`); it refuses a claim that isn't in progress with a 409. Seeding stores the plans from `context/plans.yaml` in `payout_rules`, and the approval limit comes from the settings in force, so the rules read nothing from `data/`. A new approval limit applies to the decisions recorded after it. Every input of the operation is required, including each field of a line.
  - Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `hold_payment`, `sign_off_claim`, `fail_claim`, `record_model_call`, `record_work_time`. `record_step` takes each step's `sources`, the context files a lookup came from, and none for any other step; the kinds are `screening`, `tool_call`, `tool_result`, `message`, `lookup`, `memory_search`, `memory_save`, `refusal` and `error`.
  - A complete decision record (claims manual section 14): `record_decision` takes `decided_by` and checks, in order, the request before it reads the claim (a blank reason, section or maker, an approval paying nothing, a decline or referral paying something, each a 422 whose `detail` names section 14), the claim as before, then for an approval the calculation on file for this attempt and its payout (`backend/records.py`). The record holds the calculation's lines and payout, `decided_by`, `decided_at` and `manual_version`, the claims manual's version from the documents table, and a sign-off adds who signed off and when. `hold_payment` (`POST /api/claims/{claim_id}/hold`, for the agent's key, off the Gateway) moves an approved, unpaid claim in progress to waiting for sign-off with the Gateway's reason as `gateway_refusal`; a repeat returns the claim.
  - Cost and time: `record_model_call` records one model call's input and output tokens and its cost in US dollars on a started claim, in `model_calls`, and `record_work_time` one spell of the agent's work, in `work_times`, with its start worked out from the time it's recorded less its seconds. Each has the claim's thread and the run it happened in, or none.
  - Claims: a claim moves from waiting to in progress. A decline or a referral is then decided. An approval stays in progress until `pay_claim` pays it, which decides it, or moves to waiting for sign-off when its payout is over the approval limit in force. `pay_claim` first refuses any amount over the approval limit in force with a 403, "A payout over $1,000.00 needs a handler's sign-off", before it reads the claim, so an over-limit payment gets the same answer on any claim; then it refuses a payout held for sign-off with the same message, naming the limit it was held under. A sign-off records the signed-in handler and the time on the decision and pays the approved payout in the same transaction, so the claim is decided, with no call to the agent's service. The payment shows who signed off and when. A repeat of the decision or payment already recorded returns the claim, and a different one is refused with a 409, so a step that runs again after a restart does no harm. `pay_claim` returns the claim. Each start counts as an attempt. `fail_claim` records the reason as an `error` step and puts the claim back to waiting, or after its second attempt leaves it `left_for_handler`; it refuses a claim that has a decision.
  - Starting: `start_dispatch` (`POST /api/dispatches`, body `{agents}`) asks the agent's service to start a dispatch through `backend/agent_service.py`, writes nothing and returns 202. It passes on the service's 409, and returns 503 with "The agent's service isn't running" when the service can't be reached.
  - Runs: a run is a dispatch or an evaluation, with a number, its N claim agents at once, the version of the claim agent it used with that version's model and reasoning effort, which the backend records when the run is created, a status (running, finished or stopped), its start and finish, and its claims in order in `run_claims`. Only the agent's service writes them: `create_dispatch`, `create_evaluation`, `record_run_claims`, `finish_run` and `stop_runs`, under `/api/runs`. A run in a response has each claim's line from the queue with its start, seconds and model cost in the run, the run's model cost, and its seconds once it finishes. `finish_run` builds a dispatch's summary from its claims as they stand, counting each claim once: approved, declined and referred, the payouts waiting for a sign-off (counted as approved), the claims left for a handler, and the unfinished ones, in progress or back in the queue, for the next dispatch. `stop_runs` marks every running run stopped.
  - Evaluations: `create_evaluation` records an evaluation of the evaluation set (the 25 claims in `data/claims.json`) or the held-out set (in `held_out_claims`), whole or its five `tiny` claims, and makes a waiting copy of each claim, oldest submitted first, with an id like `CLM-1104-E7` written into its record too. Copies are rows in `claims` with `evaluation_id` and `copy_of`, so every claim operation works on them, but `list_claims` leaves them out and `sign_off_claim` refuses one with a 409. `start_evaluation` asks the agent's service, like `start_dispatch`. `list_evaluations` and `get_evaluation` score each evaluation from its copies as they stand and the handlers' decisions in `handler_decisions`, with the lab's measures in `backend/scoring.py`: decision accuracy, accuracy (a payout within a dollar), the cost of mistakes ($1,500 a wrongful decline, a wrongful approval's payout, $50 a needless referral, the difference on a right approval), the straight-through rate, model cost and time per claim, and the run's time. A copy the agent didn't decide counts as a referral. No response the agent's service reads holds anything from `handler_decisions`.
  - Documents: seeding stores the policy wording and the claims manual from `context/` in a `documents` table with their titles and versions (`backend/context_files.py`, which only seeding calls), without their front matter. The backend lists their numbered sections at the end of the claim agent's instructions and gives the manual's version to each decision; the context layer serves the documents to the agent.
  - The configuration in versions: the claim agent's instructions, model and reasoning effort are kept in `versions`, each with what it changed from the version it was based on, its reason, who proposed and approved it and when, and its verdict. Version 1 is seeded from `backend/instructions/claim.md`, which gives the claim agent its goal, what it has to work from and what done looks like, on `openai/gpt-6-luna` with no reasoning (`none`), so a higher reasoning effort is an improvement a round can find. With `MODEL_NAME` set when seeding, version 1 is that model at `default`, with no reasoning effort sent; `backend/free_models.py` is the only code that reads `MODEL_NAME`, so set it in `.env` before `npm run seed`. The current version is the newest kept one. `get_current_version` and `get_version`, which the claim agent's client reads, hold the number, the instructions followed by the contents of the wording and the manual, the model and the reasoning effort, and no scores. `get_configuration` and `get_version_details` add each version's status, its diff from the version it was based on (`backend/diffs.py`, from `difflib.unified_diff` with two lines of context), and its scores: the averages of the finished whole-set evaluations rounds ran on it, empty until rounds exist.
  - Rounds of the improver: `rounds` records each round with who started it, the settings, recipe and version in force, the improver's model (`openai/gpt-6.1-sol` at medium, or the model in `MODEL_NAME` at `default`), its thread and the first evaluations the current version still needs, one on the evaluation set and two on the held-out set. One round is open at a time. `proposals` holds the improver's proposals, a change (instructions, model, reasoning effort, reason) or a recipe, and each one's review; `recipes` holds the recipe's versions, seeded from `backend/instructions/recipe.md`, and `improver_calls` the improver's model calls. `round_state.py` works out where a round has got to from these records (`first_evaluations`, `improving`, `change_waiting`, `evaluating`, `verdict`, `recipe_waiting`), and stopping a round rolls back a version it hasn't given a verdict. A proposal changes nothing, a change to a model outside the models allowed is refused as it's proposed, and a round has one approved change at most: once a handler who can sign off over the limit approves it, `create_version` makes it a version under test, refusing a model outside the models allowed with a 422. `record_review` and the dashboard's `approve_proposal` and `reject_proposal` name the proposal, and refuse with a 409 one that isn't waiting. `create_round_evaluation` makes a round's next evaluation at its agents at once, choosing its set itself: its starting version on the sets of its first evaluations, then its version under test once on the evaluation set and twice on the held-out set until the verdict, so a version's scores never change after it, refusing a version's first one when the three could cost more than what's left of the limit, estimated from the highest cost per claim seen on the version's model or, with none, on another model scaled by its prices (`spending.py`). A round's cost is its improver calls, its evaluations' model calls and the judge; once it reaches the limit, `start_claim` refuses a new claim in its evaluations and the evaluation finishes stopped, which stops a round still in its first evaluations. `record_verdict` keeps or rolls back the version by the rule in `verdict.py`, on the averages of its held-out evaluations against the current version's. `get_improver_view` gives the improver the current version, its scores, the evaluation set's wrong claims and the five right ones explained least well beside the handlers' reasons, the earlier rounds, the settings, the rule, the spending and the models allowed, and nothing from the held-out set but scores. `get_improvement` gives the dashboard the open or newest round with its stage, progress, proposal waiting and diff, evaluations and cost, every round, the versions tried and the recipes. `start_round` and `stop_round` need a handler who can sign off over the limit, and `start_round`, `approve_proposal` and `reject_proposal` reach the agent's service through `agent_service.py`. The first recipe, `backend/instructions/recipe.md`, has the improver try a model allowed, at a reasoning effort allowed for it, that neither the current version nor an earlier round's version has used, a higher reasoning effort first, before it adds rules to the instructions; `improver.md` lets a round end without a change only once none is left.
  - `GET /api/improvement`, `GET /api/configuration` and `GET /api/evaluations`, which the dashboard asks for every two seconds, score all their runs and versions, and summarize all their rounds, in a fixed number of queries however many there are. On October 4, 2026, on Supabase with eight rounds, `/api/improvement` took 17 queries and about 0.4 seconds, where it had taken 110 queries and 1.75 seconds.
- `agent/`, in parts kept apart: `connection.py` holds the one client to the backend, at `UNDERCOVER_API` or `http://127.0.0.1:8000`, and `api.py` has the claim agent's and the service's operations on it, one function each; `improver_api.py` has the improver's, and `api.py` has no way to the rounds, the scores or the settings. Its client retries a refused connection five times, about 7 seconds, since the service calls the backend as it starts. `call` sends the agent's key, read from `UNDERCOVER_API_KEY` as each request is sent, in an `X-API-Key` header, and the agent's service refuses to start without it. `uv run -m agent` reads `UNDERCOVER_API` from the shell's environment, never from `.env`, because `connection.py` reads it before the command line loads `.env`; the agent's service gets it from `.env` through `npm run dev`. `tools.py` holds the claim agent's tools and the context and state they read. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch or an evaluation. `improver.py` is the improver. `service.py` is the agent's service. `console.py` sets up the report lines and says in one line what went wrong. The agent's service creates each run, reads its version with `get_version` and builds the run's claim agents from it: its model through `agent/openrouter.py`, at its reasoning effort (`default` sends none), with a 120 second timeout and 5 retries, and its instructions. `uv run -m agent CLM-1001` uses the current version. The agent no longer reads `MODEL_NAME`.
  - The claim agent is a hand-written LangGraph graph, built by `claim_graph(llm, screener, saver, instructions, store)`, with the check for hidden instructions first (`screen`, and `refer` for a claim it flags), then a node that calls the model (`agent`), a `ToolNode` (`tools`), `pay`, and with a memory `remember`, which saves a claim the claim agent decided once its work ends and records a `memory_save` step. Its state holds the messages, the model calls so far, the check's result, and the decision and status the backend returned from `record_decision`. After a decision a decline or a referral ends the claim agent's work, an approval the backend can pay goes to `pay`, and one the backend holds for sign-off ends its work too, since the handler's sign-off pays it, each then going to `remember` when there's a memory; the graph never compares a payout with the limit itself, and its thread has nothing left to run. The agent node records every message and tool call as a step on the claim, named as the route names it, and the tool node records every tool result, or its refusal as a `refusal` step, plus the step a tool gives as its artifact: a `lookup` with the files it came from for each of the context layer's tools, and a `memory_search` for `search_memory`. The backend's refusals and calls with bad arguments go back to the model, any other error stops the graph, and the agent node stops after 30 model calls, counted across restarts. Tools run one at a time, so two decisions in one reply can't race.
  - The check for hidden instructions, `agent/screening.py`, is the one in `labs/week3day2_lab1.ipynb`: the lab's `SCREEN_INSTRUCTIONS` and `Screening` answer, its reason before `instructions_found`, asked for in a strict tool call with `with_structured_output(Screening, method="function_calling", strict=True, include_raw=True)`, which is still Structured Outputs: LangChain reads the answer after the call, so an answer it can't read comes back with the call's cost. The lab's default, `json_schema`, reads it inside the call and raises, losing the cost and the retry. The `screen` node gives it the claim as the `get_claim` tool gives the claim agent, records the call's cost with the claim's run and the result as a `screening` step, always the first on the thread, and keeps the result in the state as `screening`. A claim it flags goes to `refer`, which records a referral with a payout of zero, the check's reason and the section "Security check: no section of the wording or the manual applies", and the claim agent's model never sees it. An answer that can't be read raises `UnreadableScreening`, which the node's `RetryPolicy` tries three times in all; nothing else is retried there, so a rate limit or a timeout leaves the claim in progress and any other error fails the attempt. The check runs once for each thread: carrying on from saved progress starts after it, and a new attempt or a fresh start is checked again. Its model comes from `get_screening` (`GET /api/screening`): `openai/gpt-6-luna` at `none`, or the model in `MODEL_NAME` at `default`, outside the versions, so nothing the improver proposes changes it. The dashboard shows the step as "Security check" with a shield icon.
  - The agent writes the JSON it hands a model and records as a step with characters such as § and ’ as themselves (`agent/json_text.py`), so the steps read as the model wrote them.
  - The claim agent has twelve tools, or thirteen with a memory. Five are the app's operations, `get_claim`, `get_policy`, `get_claim_history`, `calculate_payout` and `record_decision`, which take no id from the model: they act on the claim, its policy and its customer in the agent's `ClaimContext`, and `record_decision` sends the maker, "UnderCover Agent, version N", so a claim agent can't touch another claim or another customer's records. Seven are the context layer's lookups, `lookup_term`, `describe_fields`, `get_plan`, `get_claim_rules`, `search_reference_data`, `search_documents` and `read_section`. With a memory, outside evaluations, `search_memory` searches what we remember about the claim's customer. It has no tool to pay: the graph pays through the route, and holds a payment the Gateway refuses for a handler's sign-off.
  - The two routes: `claim_graphs(version, kind, pool)` reads `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_CONTEXT` and `UNDERCOVER_MEMORY_ID` when a run's claim agents are built, and lists the route's tools then, so a context layer that isn't running stops the run at its start with one line saying so. On the Gateway (`agent/gateway.py`), the tools and the payment are the Gateway's MCP tools, `undercover-app___<operation>` and `undercover-context___<tool>`, signed with SigV4 for `bedrock-agentcore` with the AWS CLI's credentials and region, and a call the Gateway refuses reaches the model as "Refused by the Gateway: ..." and is recorded as a refusal. Directly (`agent/direct.py`), the app's operations go through `agent/api.py` with the key and the context layer's tools over MCP at `UNDERCOVER_CONTEXT` or `http://127.0.0.1:8006/mcp`. `agent/mcp_tools.py` makes each MCP call on an event loop of its own, which leaves the thread's loop alone for Mangum, in a session of its own.
  - Memory (`agent/memory.py`): with `UNDERCOVER_MEMORY_ID` set and a run that isn't an evaluation, the claim graph is compiled with `AgentCoreMemoryStore` as its store, in boto3's default region. `remember` saves the claim (its summary, the benefit claimed, the date and place of the incident and the items claimed, never the story or the documents) as a `HumanMessage` and the decision with its payout, section and reason as an `AIMessage`, with the customer as the actor and the claim as the session; nothing is saved for a claim the check referred or a failure before a decision. `search_memory` searches `("customers", <customer>)` and leaves out the claim's own summary by the namespaces each memory lists in `value["namespaces"]`, since `AgentCoreMemoryStore` 1.2.4 gives every result the prefix searched as its namespace. A memory that can't be reached leaves the claim its decision, with a warning, and a search refused.
  - Progress: `checkpoint_pool()` opens the process's pool of at most 4 connections to `DATABASE_URL`, waiting up to two minutes for a connection, and sets up LangGraph's `PostgresSaver` once, with its tables in the `undercover` schema beside the backend's. `claim_graphs(version, kind, pool)` builds a claim agent, a claim graph with a saver of its own plus its route and maker, for each claim run, since a saver lets one claim at a time read or write. The graph saves its state after every step (`durability="sync"`). The agent is synchronous throughout, since async Postgres connections don't work with Windows' default event loop. The tests use an `InMemorySaver`.
  - Cost and time: after each model call the agent node records the reply's `prompt_tokens`, `completion_tokens` and `cost` from `response_metadata["token_usage"]`, which carries OpenRouter's `usage`. `work_claim` and `carry_on` time each spell of work with `time.monotonic()` and record it however it ends, after the claim is settled. Both carry the run's id from `ClaimContext`, or none for `uv run -m agent CLM-1001`.
  - Tracing: each claim agent run is traced in Langfuse with the keys in `.env`, in a session named after the claim and its thread, such as `CLM-1001:ca130bd0-...`, as a trace named "Work claim". A claim worked in a run has `langfuse_tags: [run_id]` in its metadata. The run is invoked in a fresh `contextvars.Context`, so it is a root run even inside the dispatcher, which Langfuse needs to set the session. Without the keys, Langfuse prints a warning and sends nothing. The tests put a recorder in its place.
  - `work_claim(claim_id, run_id, agent)` starts the claim as a new attempt, with a new thread id, and runs the claim graph on that thread from a clean start. Any failure before the decision, or finishing without one, is recorded with `fail_claim`, except a rate limit or a timeout (`TRANSIENT`), which is raised again with the claim left in progress and its progress saved. A claim decided before a failure keeps its decision, the error is logged, and an approval whose payment failed stays in progress. It returns one line built from the backend's record, like `CLM-1001  approve  $420.00`, `CLM-1003  approve  $3,750.00, waiting for sign-off`, `CLM-1001  approve  $420.00, not paid yet` or `CLM-1004  failed: ..., back in the queue`.
  - `carry_on(claim_id, run_id, agent)` carries a claim in progress on from its saved progress, as the same attempt, on the same thread. A claim with nothing saved and no decision starts from the beginning on its thread. Any other carries on from its last saved step, finishing a step whose writes were saved before its checkpoint, so a claim stopped mid-node re-runs only that node; the backend treats a repeated decision or payment as done. The model call limit counts across a restart. It reports like `work_claim`, as a trace named "Carry on" in the claim's Langfuse session. `work_in_run(claim_id, run_id, new_agent)` builds a claim agent (its graph, route and maker) and carries the claim on if it is in progress or starts it if it is waiting: it's the one function the dispatcher calls. A claim whose work has ended, such as one held for sign-off, has nothing left to run.
  - The dispatcher is a LangGraph graph with no model, in the style of `labs/week2day4.ipynb`. For an evaluation, `list_claims` takes its copies, which the backend made. For a dispatch it lists the queue's claims in progress and waiting, oldest submitted first, and records them with the dispatch. `fan_out` sends each to `work_claim` with a `Send`, or goes straight to `finish_run` when there are none, and LangGraph runs up to N `work_claim` tasks at once (`max_concurrency`). `work_claim` calls `work_in_run`, and once more when the claim's first attempt failed and put it back in the queue. Its `RetryPolicy` tries a claim three times in all on a rate limit or a timeout, waiting about 10 seconds then 20, and each retry carries the claim on. On the last try, and for any other error, it reports the claim "left for the next dispatch", or "left in progress" for an evaluation's copy, and the run goes on. The service binds the harness's `work_in_run` to its claim graphs and hands it to the dispatcher. `finish_run` runs once, after every claim. The dispatcher saves no progress of its own. The tests run the `RetryPolicy` with its waits at zero.

  - The agent's service, `agent/service.py`, is a FastAPI app on port 8002 with `health`, `start_dispatch`, `start_evaluation`, `start_round` and `review_proposal`. One thing runs at a time: a dispatch, an evaluation or a stretch of a round, and a start refuses with a 409 that names what is running, such as "A dispatch is running". `start_round` creates the round, works its first evaluations through the dispatcher, then runs the improver until it pauses for a handler or ends, recording a proposal and letting go of the lock while it waits; `review_proposal` records the review and resumes it. A dispatcher that fails marks the run stopped, and the next start is accepted. ## Known gaps

- A claim with a decision but nothing saved on its thread, which only happens when someone approves a claim through the API by hand, can't be carried on: each run logs the error and leaves it in progress.
- If two processes carry the same claim on at the same moment, which the harness can't rule out, the backend still decides and pays it once. The second process's decision or payment, arriving while the first is being saved, is refused with an error, and that process logs it.
- A handler can only sign off a held payout; rejecting one comes later.
- The dispatcher's worker re-raises a rate limit or a timeout until its last try, rather than using LangGraph's `error_handler`: in LangGraph 1.2.12 a handled error is still raised from `invoke` when the worker runs beside others. A test records this, so a release that fixes it shows up.
- `uv run -m agent CLM-1001` beside a dispatch can work the same claim at the same moment; the backend still decides and pays it once.
- At 25 claim agents at once each step outside the model takes about 2.6 times as long as at 3 (0.37 against 0.14 seconds), most likely from waiting on the 4 connections a process to Supabase (see the live run below). The model itself is no slower.
- GPT-6 Luna sometimes ends its turn with a message instead of recording a decision: 4 times in the live runs below. The harness fails that attempt and the dispatch works the claim once more. A claim this happens to twice is left for a handler, as CLM-1017-E3 was.
- Langfuse loses the traces of claims stopped by `kill -9` before the service's client sent them.
- An improver call answered just as a handler stops the round isn't recorded, since a stopped round records nothing more, so the round's cost can be short by that one call. The stretch ends there.
- `/docs` and `/openapi.json` stay open. They describe the routes and grant nothing.
- Two senior handlers saving the settings at the same moment: the later save is built on the settings as its page loaded them, so it can undo the other's change.
- In a production build the page can paint once before `theme.ts` sets a saved appearance that differs from the computer's.
- A refused sign-off says the approval limit in force now, not the one the payout was held under, if they differ.
- An approval within the limit that isn't paid yet, because its payment failed or the agent stopped just before paying, can't be paid if the limit is lowered below it meanwhile: `pay_claim` checks the limit in force before it reads the claim, as the Gateway's Policy will, and only a payout held when it was decided can be signed off. It stays in progress for a handler. A test records this.
- The Improvement page re-scores every round's evaluations on each two-second refresh, which grows with the rounds run.
- A claim's decision arriving moves the agent's steps below it down once, by the decision's height: it's new content, and keeping room for a decision would leave a large empty panel on every claim. While an evaluation runs, a copy's own cost and time grow in place in their right-aligned cells.
- Rounds can't run on free models, which allow fewer requests in a day than a round needs; students on free models build and test everything.
- Stopping `npm run dev` with SIGTERM twice left a uvicorn reloader holding its port with no worker; `kill -9` on it cleared the port.
- The data dictionary in `context/` doesn't describe a decision's `gateway_refusal`; it's data governance's file, so it's left as it is.
- AgentCore turns a saved claim into memories in the background, about 90 seconds after the save in our team's experiment, so a customer's next claim worked straight away may not find the first.
- A crash after a claim is decided or held and before `remember` finishes loses that claim's memory, or keeps only its first event: the dispatcher only carries on claims in progress, so nothing runs `remember` again. An approval stopped before its payment is carried on, paid and remembered once.
- `uv run -m agent` on an evaluation's copy, which nothing does, would work it with the memory: memory follows the kind of run, and a claim worked on the command line has none.
- The live runs used the direct route with memory off; the Gateway's names, its refusals and the memory are covered by the tests with stand-ins, and by the deployment notebook.

## Supabase

The backend's tables and the checkpointer's are in the `undercover` schema. Row Level Security is off on them, and Supabase's table listing warns about that, but the schema isn't exposed through Supabase's Data API: the `anon`, `authenticated` and `service_role` roles have no access to it, and Supabase's security advisor reports nothing. The backend and the agent connect as `postgres`, the tables' owner.

## Review of the harness

On September 30, 2026, the head of engineering's review (`docs/HUMAN_REVIEW_HARNESS.md`) found that the harness was unfit for a PR:
- The agent had more than 20 hard-coded backend URLs and two ways of calling the backend.
- `queue.py` reached into `main.py`.
- The tools were spread across files, and state was passed through closures instead of LangChain's `context_schema`.
- The instructions were step-by-step scripts.

The agent was rebuilt as `api.py`, `tools.py` and `harness.py`, and the instructions were rewritten as goals. Fresh reviewers then went through the backend, the dashboard and the tests, and their fixes are in the same change.

These problems passed every check. Each phase was built, checked against its criteria and committed, and nobody read the code the way a reviewer reads a PR. `docs/CODE_STANDARDS.md` now sets the structural rules the review found broken. `docs/PROCESS.md` now requires a review by a fresh subagent before every commit, and a design in every plan.
