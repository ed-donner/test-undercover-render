# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, so each query is written once for both databases. With `DATABASE_URL` in its environment it uses the Supabase Postgres database through the session pooler, with every table in the `undercover` schema and at most 4 connections, waiting up to two minutes for one; otherwise SQLite, as in the tests. `main.py` holds the app and the claim, document and handler operations; `runs.py`, `configuration.py` and `improvement.py` are `APIRouter`s with the operations on dispatches and evaluations, on the claim agent's configuration and settings, and on the improver's rounds; they share the `Database` and `SignedIn` dependencies in `dependencies.py` and the claim views in `views.py`. The claim agent's configuration (its instructions, model and reasoning effort) and the improver's recipe are versioned records the backend owns, with diffs from `difflib`, and the backend applies the rule that keeps or rolls back a version. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount, and it refuses any amount over the approval limit in force before it reads the claim. A handler's sign-off records the payment itself. `get_agent_api` (`GET /api/agent/openapi.json`) serves the OpenAPI document of the claim agent's eight operations for an AgentCore Gateway, built in `agent_api.py` with `get_openapi`, with no `servers` and no security schemes. `get_screening` names the model the check for hidden instructions runs on, `openai/gpt-6-luna` at `none` or the model in `MODEL_NAME`, outside the versions. The payout rules are in `backend/payout.py`, and the scoreboard's measures in `backend/scoring.py`. The backend calls the agent's service to start a dispatch, an evaluation or a round and to pass on a review, at `UNDERCOVER_AGENT` in the environment or `http://127.0.0.1:8002`.
  - Who may call what: every route but `health` has one gate in `dependencies.py`. `AgentKey` needs the agent's API key, which the agent's side sends in an `X-API-Key` header and `api_key.py` compares with `UNDERCOVER_API_KEY` with `secrets.compare_digest`, read through FastAPI's `APIKeyHeader`; `HandlerOrAgent`, on the four reads both use and on `get_agent_api`, takes the key or a signed-in handler; every other route needs a signed-in handler. The key never stands in for a handler. With no key set, every route that needs it refuses.
  - Sign-in: Supabase Auth. `auth.py` checks each access token with PyJWT's `PyJWKClient` against the project's public keys at `VITE_SUPABASE_URL`, and the backend finds the handler by the token's email.
  - The judge: Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions endpoint with the `openrouter` package, called once, in `judge.py`, at `JUDGE_URL` or `https://openrouter.ai`.
  - `free_models.py` is the one place that reads `MODEL_NAME`: with it set, seeding makes that model version 1 and the only model allowed, and the improver uses it too.
- `agent/`: six parts. `connection.py` holds the one client to the backend, at `UNDERCOVER_API` or `http://127.0.0.1:8000`, and sends the agent's API key from `UNDERCOVER_API_KEY` with every request, read as each request is sent. `api.py` is the claim agent's and the service's API on it: claims, runs, the configuration's versions, the documents, the payout rules and the records of cost and time; `improver_api.py` is the improver's: the rounds, the results, proposals, versions, recipes and verdicts. `tools.py` holds the claim agent's tools, the context they read and the claim graph's state, and the tools that act on the claim read it from the agent's context through `ToolRuntime`. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch or an evaluation. `improver.py` is the improver. `service.py` is the agent's service, a FastAPI app the backend calls to start a dispatch, an evaluation or a round and with a handler's review, which refuses to start without the API key; in the cloud the agent runs as a service like this. `screening.py` is the check for instructions hidden in a claim, from `labs/week3day2_lab1.ipynb`. `console.py` sets up the report lines and says in one line what went wrong.
  - The claim agent is a hand-written LangGraph `StateGraph`, built by `claim_graph(llm, screener, saver, instructions)`: first the check for hidden instructions (`screen`), on the model `get_screening` names, which reads the claim with Structured Outputs in a strict tool call and has a `RetryPolicy` for an answer it can't read, then `refer` for a claim it flags or else a node that calls the model, a `ToolNode` and a node that pays an approval the backend can pay at once. A payout the backend holds for sign-off ends the graph, since the sign-off pays it. Its nodes record each reply, tool call, tool result and section read on the claim, and each model call's tokens and cost, return refusals to the model and limit the model calls. It saves its state after every step with LangGraph's `PostgresSaver` in the same Supabase database, with `durability="sync"`, so the agent always needs `DATABASE_URL`, even when the backend runs on SQLite. Each claim run gets a saver of its own on the process's shared `ConnectionPool` of at most 4 connections, since a saver lets one claim at a time read or write. The agent is synchronous throughout, because async Postgres connections don't work with Windows' default event loop.
  - The dispatcher is a LangGraph `StateGraph` with no model, in the style of `labs/week2day4.ipynb`: `list_claims` lists the claims, `fan_out` sends each to the `work_claim` node with a `Send`, `max_concurrency` caps the claim agents at once at N, and `finish_run` runs once after them all. The `work_claim` node has a `RetryPolicy` for rate limits and timeouts. It saves no progress of its own.
  - The harness's entry points are `work_claim(claim_id, run_id, graph)`, which works one claim as a new attempt, `carry_on(claim_id, run_id, graph)`, which carries a claim on from its saved progress, and `work_in_run(claim_id, run_id, new_graph)`, the one function the dispatcher calls, which does either on a graph of its own. Each times its spells of work and records them with their run.
  - Every claim graph run is traced in Langfuse, in a session named after the claim and its thread, and tagged with its run's id in `langfuse_tags`.
  - The claim agents of a run use its version's model and reasoning effort, `openai/gpt-6-luna` with no reasoning (`none`) in version 1, so a higher reasoning effort is an improvement a round can find. Each model call's cost comes from OpenRouter's `usage.cost` on the reply. `uv run -m agent` reads `UNDERCOVER_API` from the shell's environment, never `.env`; the agent's service gets `.env` from `npm run dev`.
  - The improver is a LangChain `create_agent` on the round's model, `openai/gpt-6.1-sol` at medium by default, with the lab's four tools. `HumanInTheLoopMiddleware` pauses it for a handler's approval, with its progress saved by a `PostgresSaver` of its own on the round's thread; `ModelCallLimitMiddleware` caps its model calls in a round at 20; parallel tool calls are off. Each stretch of its work is traced in Langfuse in the round's session.
- `dashboard/`: React, Vite and TypeScript, with icons from `lucide-react`. `auth.ts` is the one module that uses `@supabase/supabase-js`, with `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, which Vite reads from the repo root's `.env` in development and production mode, never in the tests.
- `e2e/`: Playwright tests, with stand-ins for the agent's service, Supabase Auth and the judge.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Supabase session pooler connection string (`DATABASE_URL`), the Supabase project's address and publishable key (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`), the handlers' password for browser checks (`HANDLER_PASSWORD`), the agent's API key (`UNDERCOVER_API_KEY`), the Langfuse keys (`LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`), and optionally `JUDGE_URL` and `MODEL_NAME`.

## Deployment

- `npm run build` builds the dashboard into `dashboard/dist`, with `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the environment or, where it doesn't set them, from `.env`, so the build works on a server with no `.env`. When `dashboard/dist` exists, the backend serves it: its files at their own paths and `index.html` for any other path outside `/api/` (`backend/dashboard.py`).
- The package holds `backend/` and `data/`, without `tests/` or `__pycache__`, `dashboard/dist/`, and the `server` dependency group of `pyproject.toml` installed for Linux and Python 3.12 (`uv export --only-group server`, then `uv pip install --target ... --python-platform x86_64-manylinux2014 --python-version 3.12 --only-binary :all:`). `npm run check:server` checks that the backend imports with only that group installed. At run time the backend imports nothing from outside the package, reads files only from it, and writes none.
- On AWS Lambda the handler is `backend.main.handler` (Mangum, with the startup hook off, so nothing seeds the database). On a web server the app is `backend.main:app`, as in `uv run -m uvicorn backend.main:app`.
- The function's environment is `DATABASE_URL` on Supabase's transaction pooler (port 6543), `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`. With `AWS_LAMBDA_FUNCTION_NAME` set, as Lambda sets it, the backend opens a connection for each request and keeps none (SQLAlchemy's `NullPool`), with prepared statements off (psycopg's `prepare_threshold=None`), which the transaction pooler needs.
